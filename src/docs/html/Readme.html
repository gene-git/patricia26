1. patricia26

1.1. Overview

A Patricia tree is designed to map some data to a network. A network is a range of consecutive IP addresses. Since an IP address is a number, this provides a way to attach data to a range of numbers.

For example, it can be used to associate a geographic location, a country for example, with an IP network.

patricia26 implements this as a compiled library and provides a Python module that uses it.

patricia26 has two components: A Patricia Trie library and a Python module using the library. It provides:

  • a modern, C23 compliant (Linux) version of the the original C-code.

  • a Python module generated using Cython that uses the shared c-library.

  • an autogenerated API reference guide for both the C and Python code.

The project name made unique to allow the C library to be installed alongside the original and to avoid any conflict with other similar Python modules such as PyTricia.

This project was forked from Dave Plonka’s Patricia Library along with some modifications of the core c-code by Joel Sommers’ PyTricia. The main change introduced in PyTricia changed node->prefix from prefix_t * to a prefix_t thereby reducing the number of malloc calls.

The C-code has been tidied some and is now C23 compliant. See the meson.build file for more details on compile and link options.

The Python module, Patricia26, uses the C library libpatricia16.so. The shared library must be installed and available for the Python module to run.

Using Cython to generate the Python module keeps the module highly performant. Uusing a shared patricia library allows for:

  • C and Python applications to use the same library.

  • the core patricia library to be built with stringent compile and link options.

The Cython generated C-code is built using slightly different options than the core c-clibrary since manually tidying Cython generated c-code is not practical. Consequently, we use less stringent compile options on the Cython code.

While this is working well for our own use cases, should any issues arise, please let us know.

The documentation including the C and Python API reference is in patricia26.pdf in the Docs directory and is also installed in usr/share/patricia26/

The Python module, Patricia26 offers similar functionality to PyTricia Both modules are very fast and are built on top of the same original core Patricia C-code. We have used PyTricia and found it to be robust and works well.

Patricia26 can be somewhat faster, especially for bulk and cidr lookups.

The API is a little different, but changing from one to the other is quite straightforward. Please see Migrating from PyTricia.

1.1.2. Additional Python Approach

There is a tentative Python module, Patricia_int, that uses integers / ipaddress instead of IP and CIDR strings. However, this version is significantly slower, probably due to Python not using simple 32 and 128 bit number representations that can be mappped directly to C, thus necessitating additional conversion overhead that inflicts a pretty big performance penalty. Consequently, we’re not using this class and so it has not had the usage and testing that Patricia26 class has.

1.2. Patricia26 Python class

The Python module wraps the core patricia C-functions. This is a short highlight on using Pytricia26. Please see the documentation section with the Reference API guide which provides details on the class and its member functions.

Instantiate Class

The class internally keeps both a 32 bit IPv4 tree and a 128 bit IPv6 tree, so instantiating for either is done the same way.

from patricia26 import Patricia26
pyt = Patricia26()

Saving Values

Values are inserted into the tree either one at a time or from a list of tuples.

For example:

pyt[ip_or_cidr] = value

or

pyt.insert(ip_or_cidr, value)

or

items = [(ip_or_cidr_1, value_1), ((ip_or_cidr_2, value_2), ... ]
pyt.bulk_insert(items)

Looking up Values

The best way to lookup the value associated with the longest prefix match (LPM) is to use the optimized lookup() method.

The dictionary subscript syntax (pyt[ip_or_cidr] can also be used for both CIDRs or IP addresses.

When looking up a list of items, bulk_lookup(list_of_ip_or_cidrs) is much faster than looping over pyt.lookup(). It returns a list of values.

When the value and it’s associated LPM prefix are needed, then lookup_lpm() returns a tuple of (lpm, value).

Examples:

value = pyt.lookup(ip_or_cidr)
value = pyt[ip_or_cidr]
(lpm, value) = pyt.lookup_lpm(ip_or_cidr)

with ip_or_cidr ~ ‘10.0.0.2’ or ‘10.1.0.0/22’

results = pyt.bulk_lookup(cidrs)

is much faster than

results = []
for cidr in cidr_list:
    results.append(pyt.lookup(cidr))

1.3. Performance

The benchmark code is available in the tests directory. We test lookups on both IP and CIDR inputs using bulk_lookup() as well as looping on lookup(). Similarly to retrieve both the lpm and it’s associated value.

Please view these test results as a rough guide only. We recognize there may be ways to improve performance that we may not have taken advantage of.

Doing lookups on plain IP adresses is a bit faster than on CIDR blocks since the latter involves some prefix length calculations. Bulk lookups are substantially faster than using a loop.

Bulk IP lookups can be two to three times as fast as doing the same in a loop: 68 million per second versus 23 million per second. Bulk CIDR lookups at 65 million per second compared to 25 million per sec using a loop.

Bulk lookups should be used with care if the size of the input list is very large due to potential memory pressure. The benchmark tests worked well with 5 million and 50 million IP/CIDRs iterations, with the performance remaining roughly constant. There is variability with different number of iterations but the overall picture remains clea. Tests were run on a laptop with 32 GB of memory.

We should write some additional benchmarks using larger trees, but the high level picture is that these modules are both pretty decent.

Looking up the pair of (LPM prefix, value) using looup_lpm() is a lot slower than retrieving the value alone (8.5 million per second). So, if the lpm prefix is not needed, its far better to use lookup() or bulk_lookup().

Pytricia*s performance doing value lookups is similar to looping in *Patricia26 and of course slower than bulk_lookup().

The tests lookup the same IP / CIDR repeatedly which is obviously not terribly realistic. So with that in mind this is sample bencmark output. All benchmarks run with 50 million iterations:

           Patricia26 (50,000,000 iterations)
  Method    Input       Lookup    Seconds  Lookups / sec
    Bulk       IP          val    0.7300    68,489,951
    Bulk     CIDR          val    0.7627    65,552,597
    Loop       IP          val    2.1655    23,089,855
    Loop     CIDR          val    1.9984    25,019,973
    Loop     CIDR   (lpm, val)    5.6163     8,902,680
    Loop       IP   (lpm, val)    5.5182     9,060,900


             PyTricia (10,000,000 iterations)
  Method    Input       Lookup    Seconds  Lookups / sec
-------- -------- ------------ ---------- --------------
   [key]       IP          val    2.0406    24,502,376
     get       IP          val    3.2581    15,346,357
     get     CIDR          val    3.6105    13,848,587
    getk     CIDR   (lpm, val)    9.3112     5,369,895
    getk       IP   (lpm, val)    8.9636     5,578,110

The Patricia26 tests use pyt.lookup(), pyt.bulk_lookup() and pyt.lookup_lpm(). The lpm lookups carry a burden of additionally providing the prefix string which shows degraded performance compared to simply looking up the value.

The PyTricia tests use pyt[ip] and pyt.get(cidr) and retrieve the (lpm, value) ~ (lpm = pyt.get_key(), pyt[lpm])

1.3.1. Pickling: Compact File Size

When Python uses pickle to save a Patricia26, the class pickles the actual data of (prefix, value) pairs in the tree. The glue modes are automatically re-created by the c-clibrary when unpickling and are not saved in the pickled file. This leads to smaller pickled files, and the savings can be very significant. Smaller files naturally means faster IO.

For example, for a tree with 355,951 IPv4 prefixes and their associated values the pickled file size is approximatrly 4MB; if the glue nodes are kept the size would be about 25 MB - so file size is around 16% of what it would be had we retained all the glue nodes.

1.4. Documentation

The package includes a pre-built PDF guide in Docs/patricia26.pdf The PDF and HTML version can be built by running:

make latexpdf ; make latexpdf
make html

Building the docs requires sphinx and hawkmoth. The documentation includes an auto-generated API Reference Guide that covers both the Patricia C-library and the Patricia26 Python class.

The PDF documentation is installed in usr/share/patricia26
